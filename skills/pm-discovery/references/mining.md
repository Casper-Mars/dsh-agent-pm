# 需求挖掘：补证据时的采集流程

`pm-prd` 门禁 1 失败（证据不足、只有 E4/E5）时读。挖掘不是独立产出，是补证据的手段；采完回到主循环重新定级。

## 一、平台路由

| 平台 | 参考文档 | 采集对象 |
|---|---|---|
| V2EX | `references/v2ex.md` | 板块热门主题与回复 |
| Hacker News | `references/hackernews.md` | 首页 / Ask / Show 帖子与评论 |
| Product Hunt | `references/producthunt.md` | 首页热门产品与用户评论 |

用户没指定平台先问一句；多个平台逐个跑完整流程，不混批。

## 二、步骤（连续执行，不逐步确认）

1. **前置检查**：按参考文档确认入口、是否需登录、限频；不满足就地降级并说明。
2. **采集**：按入口与字段写入本次清单；采集量 = 批数 × 每批条数，宁少勿滥。
3. **分批**：每批 5–8 条，固定不变；每批开始前在待办建「第 N 批：条目 a–b」。
4. **逐条分析**：每条只答四件事——谁在抱怨、具体场景、现在怎么替代、有无付出意愿证据。
5. **汇总**：只带结论不带原文；跨条目合并并标出现次数与平台分布；按「信号强度 × 影响面」排序。
6. **落盘**：写 `docs/research/<平台>-<日期>.md`，`git commit`。
7. **回主循环**：把新证据按 E1–E5 补进诊断卡片，重跑门禁 1。

## 三、分批铁律

1. 每批 5–8 条，不因「看起来简单」加量。
2. 批间必须更新待办，否则该批未完成。
3. 汇总不回头重读原文；复核按编号回批次。
4. 启动后不中途问「是否继续」；只在人工操作或工具不可用时中断。

## 四、采集字段

| 字段 | 说明 |
|---|---|
| id | 本次运行稳定编号，用于批次与报告引用 |
| platform | 平台名 |
| title | 标题或产品名 |
| source | 来源标识，报告用编号引用，不放链接 |
| heat | 热度（回复数 / 点数 / 投票数） |
| excerpt | 关键短语，不超过一句 |
| evidence | E1–E5 |
| pain | 真实痛点：是 / 否 / 证据不足 |

热度不是需求强度：heat 只用于排序候选，不作为定级依据。

## 五、报告结构

```markdown
# <平台> 需求挖掘报告 <日期>
## 结论
- 值得做：<方向>（信号：强/中，证据：E?）
- 不值得做：<方向>（原因）
## 需求清单
| # | 需求 | 目标用户 | 现有替代 | 信号 | 证据 | 出现次数 |
## 丢弃记录
- 共分析 N 条，丢弃 M 条，主要原因：……
## 未决项（无则写「无」，不硬凑）
```

## 六、反例

- 一次性把上百条塞进上下文再「一起分析」——必然漏读。
- 把点赞数、投票数当需求强度。
- 汇总整段贴原文——报告无法读。
- 「多平台都提到了所以是强信号」——没有一条行为证据。
