# 发布与 GTM

发布不是「代码上线」，是「用户知道变了什么，并且能安全地用上」。

## Iron Law

> 没有回滚方案，不许发布。

## 什么时候用 / 不用

- 用：版本发布、功能灰度、release notes、客服/销售赋能、发布后监控安排。
- 不用：代码合并、CI/CD 配置、线上故障处理（交 Dev / CTO）。

## 流程

1. **定发布级别**：内部 / 灰度 / 全量；依据影响面与可逆性，见 `references/launch-tiers.md`。
2. **过发布清单**：逐项检查，模板见 `assets/launch-checklist.md`。
3. **写回滚方案**：触发条件、执行人、回滚步骤、数据兼容；没有就不发。
4. **写发布说明**：用户语言，不贴 commit；模板见 `assets/release-notes.md`。
5. **做赋能**：客服 FAQ、销售话术、文档更新；见 `references/gtm-enablement.md`。
6. **安排监控**：指标、告警、值班人、观察窗口。
7. **发布后 24 小时**：确认指标与反馈，异常按回滚方案处理。
8. **交 `pm-metrics` 做 readout**。

## 门禁

| # | 门禁 | 通过线 | 不过怎么办 |
|---|---|---|---|
| 1 | 清单 | `assets/launch-checklist.md` 全绿 | 推迟 |
| 2 | 回滚 | 有触发条件、步骤、执行人 | 不许发布 |
| 3 | 说明 | 用户能看懂「变了什么、对我有什么影响」 | 重写 |
| 4 | 赋能 | 客服能回答前 10 个问题 | 补 FAQ |
| 5 | 监控 | 指标与告警已配置 | 补齐 |
| 6 | 灰度 | 有放量节奏与停止条件（如适用） | 补方案 |

## 输出契约

发布包 = 发布说明 + 清单 + 回滚方案 + 客服 FAQ + 监控项。五件齐全才算准备好。

## 反合理化

| 借口 | 现实 |
|---|---|
| 改动很小，不用回滚 | 小改动也可能引发大故障 |
| 先全量，出问题再说 | 全量是不可逆实验 |
| 用户不看发布说明 | 不看和没有是两回事 |
| 客服会自己看代码 | 客服看的是话术与边界 |
| 灰度太慢，直接上 | 灰度是最便宜的风险控制 |

## 红旗

- release notes 是 commit 列表。
- 回滚方案写「重新部署旧版本」但没有数据兼容说明。
- 没有值班人。
- 客服在发布当天才知道。
- 灰度没有停止条件。

## 交接

- 发布执行与故障处理：Dev / CTO。
- 指标与读数：`pm-metrics`。
- 复盘：`pm-retro`。
