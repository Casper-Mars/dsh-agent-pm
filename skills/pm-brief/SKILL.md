# 决策简报（人类层）

PRD 写给执行者，简报写给决策者。同一份需求，两个投影：PRD 求完整，简报求能被拍板。

## Iron Law

> 一页之内没有结论、取舍与拍板点，不算简报。

## 什么时候用 / 不用

- 用：`m` / `l` 需求在 `pm-prd` 产出后附一份简报；用户说「看不懂」「太长」「给我一页」「要不要做」；评审前把 PRD 降维。
- 不用：`xs` / `s`（产物本身就在一页内，直接给，不另出简报）；技术方案（交 CTO）。

## 六段结构（顺序固定，缺段即不合格）

1. **结论**：一句话说做什么、一句话说不做什么；再一句话说不做会怎样。
2. **关键取舍**（0–3 条）：每条一行，写「选项 → 选择 → 代价」。没有取舍只有执行，写「无取舍」。
3. **一张图**：用户路径或状态变化，Mermaid 或一行链路。画不出来，说明关系还没想清。
4. **需要拍板**（0–3 条）：每条给「默认选项 + 不拍板的后果 + 谁定」。零条就写「无需拍板，按默认执行」。
5. **最大风险与反转信号**：最可能怎么错；看到什么就停、改方案或回退。
6. **详情**：PRD 路径 / 链接 + 版本号。正文不复制。

模板见 `assets/brief-template.md`；内容归属与质量判据见 `references/brief-vs-prd.md`。

## 字数与格式

- ≤600 字（不含标题行、链接行与图；图按代码块计）。超了先删，不许缩字号糊弄。
- 每段第一句就是结论，后面才是支撑。
- 不复述背景、不贴 AC 全表、不贴指标表、不贴数据模型、不解释流程。
- 不用多级嵌套列表；取舍可用三列小表，其余用短段。

## 生成顺序

先写简报，再写 PRD。反过来写，结论必然被埋在正文中段。
把既有文档降维时：通读全文 → 只抽「决策所需」→ 每个被删的细节留一个指针（`§X` 或链接）→ 按六段重排。

## 自检（机械可验的部分）

- [ ] 六段齐全
- [ ] ≤600 字
- [ ] 结论段同时有「做什么」与「不做什么」
- [ ] 每条取舍都写了代价
- [ ] 每条拍板项都有默认选项
- [ ] 风险段有可观察的反转信号
- [ ] 没有整段搬运 PRD（与原文重复 < 30%）

## 反合理化

| 借口 | 现实 |
|---|---|
| 细节不能删，评审要看 | 评审看取舍，细节在 PRD 里；简报给指针 |
| 一页放不下 | 放不下说明还没决定什么不重要；先删到能放 |
| 多写点显得完整 | 完整是 PRD 的职责，简报的职责是让人做决定 |
| 图以后再补 | 画不出的图 = 还没想清的关系 |
| 拍板项先空着，等他们问 | 空着等于把决定推给读者；给默认选项与后果 |
| 只是内部文档，不用这么讲究 | 内部文档的读者也要做决定，头痛的成本一样收 |

## 红旗

- 简报里出现完整 AC 表、指标五要素表、字段表。
- 结论写成三段以上。
- 取舍只写「选了 A」，不写代价。
- 拍板项没有默认选项，或没写谁来定。
- 风险写成「注意兼容性」「关注体验」这类不可观察的话。
- 把「背景」「现状」写成第一段。

## 输出

- **随需求交付一起提交**：交付需求时把简报作为第二个产物一并提交（当前平台的交付工具支持简报字段时直接用它；不支持时随交付消息给出正文）。
- 本地留档：与 PRD 同目录的 `<主题>.brief.md`，便于回溯。
- 只做判断时直接放对话首屏。
- 最后回一个可访问位置（路径、平台附件编号或链接）。
