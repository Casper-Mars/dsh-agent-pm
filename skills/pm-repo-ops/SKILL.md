# GitHub 仓库运营

一次处理一批信号，输出可审计的决策：接受、暂缓、补信息、重复、不做。

## Iron Law

> 不评审代码、不承诺排期；关闭必须有理由。

## 什么时候用 / 不用

- 用：新 issue / 新评论 / 新 PR / PR 评审 / release / 社区问答。
- 不用：代码质量、CI、依赖升级、安全修复（交 CTO / Dev）、技术方案设计。

## 流程

1. **读实时状态**：拉当前 issue / 标签 / 评论 / 关联 PR，webhook 快照只作线索。
2. **归一化**：去重（找 canonical）、过滤 bot 与自己、分类（bug / feature / question / docs / security）。
3. **按事件路由**：每条事件只进一个 workflow；路由表见 `references/event-routing.md`。
4. **五道判定**：真问题？谁的问题？现在做不做？谁接？怎么关或推进？证据分级沿用 E1–E5。
5. **写回**：一条评论 + 一组标签；评论模板见 `assets/triage-comment.md`，标签定义见 `references/label-taxonomy.md`。
6. **状态推进**：按状态机流转，关闭原因必须写；规则见 `references/issue-lifecycle.md`。API 调用、幂等标记与限流约定见 `references/github-api.md`。
7. **汇总**：本轮结论数量、需要人类拍板的前 3 条、链接。
8. **交接**：需要技术判断交 CTO；接受且要做走 `pm-prd`；进入交付走 `pm-handoff`。

## 门禁

| # | 门禁 | 通过线 | 不过怎么办 |
|---|---|---|---|
| 1 | 去重 | 已搜索同义 issue | 继续搜，不重复开 |
| 2 | 分类 | 类型 + 状态各一个 | 补标签 |
| 3 | 证据 | 结论不高于证据等级 | 降级或标「待验证」 |
| 4 | 评论 | 结论 / 依据 / 下一步与未决 三段；无未决并入下一步，不留空槽 | 重写 |
| 5 | 关闭 | 有理由与重开路径 | 不关闭 |
| 6 | 幂等 | 评论带 `<!-- repo-ops:ack:<delivery_id> -->` | 补标记 |

## 输出契约

每条 issue 一条评论，三段：结论、依据、下一步与未决（无未决只写下一步）。标签：类型 1 个 + 状态 1 个 + 优先级 0–1 个。

## 反合理化

| 借口 | 现实 |
|---|---|
| 用户很急，先答应 | 承诺排期是把风险转给开发 |
| 这个需求很明显 | 明显不等于有证据 |
| 先关掉，以后再说 | 关闭必须有理由与重开路径 |
| 顺手把代码改了 | PM 不碰代码，越界会破坏评审 |
| 评论多一点显得负责 | 刷评论不是 triage，重复结论不重复发 |
| 多写一条未决显得周全 | 未决是缺失项清单，不是礼貌用语；没有缺失就不写 |

## 红旗

- 在公开 issue 讨论安全细节。
- 批量关闭或无理由关闭。
- 把单用户偏好升级为普遍需求。
- 用点赞数当需求强度。
- 改了人类设置的标签又改回去。

## 交接

- 技术判断：CTO，附 issue 链接、证据、未决问题。
- 需求定义：`pm-prd`。
- 交付：`pm-handoff`。
- 发布说明：`pm-launch`。
