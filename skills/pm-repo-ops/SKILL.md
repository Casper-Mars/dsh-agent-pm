# GitHub 仓库运营

一次处理一批信号，输出可审计的决策：接受、暂缓、补信息、重复、不做。

## Iron Law

> 不评审代码、不承诺排期；关闭必须有理由。

## 什么时候用 / 不用

- 用：新 issue / 新评论 / 新 PR / PR 评审 / release / 社区问答。
- 不用：代码质量、CI、依赖升级、安全修复（交 CTO / Dev）、技术方案设计。

## 变更分级（weight）

流程只有一条：需求 → 技术方案 → 拆解 → 开发。weight 只决定每层文档多厚，
不决定走不走流程。

| 问 | 判定 |
|---|---|
| 用户可观察行为会变吗？ | 不变 → `xs` |
| 会改对外契约吗（API 形状 / 数据格式 / 权限 / 计费 / 导出）？ | 会 → 至少 `m` |
| 有需要人拍板的取舍或新概念吗？ | 有 → 至少 `m`；没有 → `xs` / `s` |

| weight | 需求产物 | 上限 |
|---|---|---|
| `xs` | 一句话需求（下面格式，直接写进需求卡 body） | 5 行 |
| `s` | 变更卡（`pm-prd` 的单页模板） | 1 屏 / 600 字 |
| `m` | 九章 PRD | 既有规范 |
| `l` | PRD + 立项 | 既有规范 |

一句话需求格式（`xs`）：

```text
问题：<一句>
期望：<一句可观察行为>
验收：1) <可观察结果> 2) <可观察结果>
级别：xs
```

规则：

- 判不了默认 `m`，并在评论里写明缺哪条依据。
- 需求卡 body 第一行必须是 `级别：<weight>`；没写不许交接。
- 上游 `xs`，技术方案超过半屏或出现数据模型 / 部署 / 观测章节 → 判为膨胀，退回。
- AC 不能省：一句话需求可以只有一条验收，不写验收就不算需求。

## 流程

1. **读实时状态**：拉当前 issue / 标签 / 评论 / 关联 PR，webhook 快照只作线索。
2. **归一化**：去重（找 canonical）、过滤 bot 与自己、分类（bug / feature / question / docs / security）。
3. **定 weight**：按「变更分级」三问判定，并在评论与标签中写明依据。
4. **按事件路由**：每条事件只进一个 workflow；路由表见 `references/event-routing.md`。
5. **五道判定**：真问题？谁的问题？现在做不做？谁接？怎么关或推进？证据分级沿用 E1–E5。
6. **写回**：一条评论 + 一组标签；评论模板见 `assets/triage-comment.md`，标签定义见 `references/label-taxonomy.md`。
7. **状态推进**：按状态机流转，关闭原因必须写；规则见 `references/issue-lifecycle.md`。API 调用、幂等标记与限流约定见 `references/github-api.md`。
8. **汇总**：本轮结论数量、需要人类拍板的前 3 条、链接。
9. **交接**：需要技术判断交 CTO；需求按 weight 产出（`xs` 直接写需求卡，`s`/`m`/`l` 走 `pm-prd` 对应模板）；进入交付走 `pm-handoff`。

## 代码证据前置

要引用代码、复现行为或核对实现时，先同步仓库再下结论：

1. 仓库地址取 issue / 派单里的 `git_url`；本地没有就 `gh repo clone <url> -- --depth=50`。
2. `git fetch --prune origin`，切默认分支；工作区脏先 `git stash`，不要覆盖。
3. 记录 `git rev-parse HEAD`，评论 / PRD 里的代码证据写明基于哪个 commit。
4. 只读核对，不改代码、不提交；需要修复交 CTO / Dev。

## 门禁

| # | 门禁 | 通过线 | 不过怎么办 |
|---|---|---|---|
| 1 | 去重 | 已搜索同义 issue | 继续搜，不重复开 |
| 2 | 分类 | 类型 + 状态各一个 | 补标签 |
| 3 | 证据 | 结论不高于证据等级 | 降级或标「待验证」 |
| 4 | 评论 | 结论 / 依据 / 下一步与未决 三段；无未决并入下一步，不留空槽 | 重写 |
| 5 | 关闭 | 有理由与重开路径 | 不关闭 |
| 6 | 幂等 | 评论带 `<!-- repo-ops:ack:<delivery_id> -->` | 补标记 |

## 输出契约

每条 issue 一条评论，三段：结论、依据、下一步与未决（无未决只写下一步）。
标签：类型 1 个 + 状态 1 个 + 优先级 0–1 个 + weight 1 个（`size:xs` / `size:s` / `size:m` / `size:l`）。
需求产物按 weight 选：`xs` 用上面的四行格式；`s` 用 `pm-prd` 的单页模板；`m`/`l` 用九章 PRD。

## 反合理化

| 借口 | 现实 |
|---|---|
| 用户很急，先答应 | 承诺排期是把风险转给开发 |
| 这个需求很明显 | 明显不等于有证据 |
| 先关掉，以后再说 | 关闭必须有理由与重开路径 |
| 顺手把代码改了 | PM 不碰代码，越界会破坏评审 |
| 评论多一点显得负责 | 刷评论不是 triage，重复结论不重复发 |
| 多写一条未决显得周全 | 未决是缺失项清单，不是礼貌用语；没有缺失就不写 |
| 模板在手，写全一点保险 | 文档规模不得超过决策规模；`xs` 写满章是缺陷，不是尽责 |
| 先按 `m` 写，反正能删 | 厚度由三问定，不由感觉定；只有判不了才默认 `m` 并说明依据 |

## 红旗

- 在公开 issue 讨论安全细节。
- 批量关闭或无理由关闭。
- 把单用户偏好升级为普遍需求。
- 用点赞数当需求强度。
- 改了人类设置的标签又改回去。

## 交接

- 技术判断：CTO，附 issue 链接、证据、未决问题、`级别`。
- 需求定义：按 weight 选厚度；需求卡首行必须写 `级别：<weight>`。`xs` 不另开会话，直接写进需求卡；`s`/`m`/`l` 走 `pm-prd`。
- 交付：`pm-handoff`。
- 发布说明：`pm-launch`。
