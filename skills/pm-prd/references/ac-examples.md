# AC 正反例

`pm-prd` 的 AC 规则展开。写验收标准时读。

## 合格的 AC

| 编号 | 验收标准 | 判定方式 |
|---|---|---|
| AC1 | 未登录用户点击「导出」时展示登录引导，不触发下载 | 手工点击 + 网络面板无导出请求 |
| AC2 | 单次导出 1 万行数据在 30 秒内完成 | 跑压测脚本，记录 P95 耗时 |
| AC3 | 任务创建失败时页面提示错误码，且不产生脏数据 | 断网重试一次，查数据库无新增行 |

三要素齐全：**触发条件**（谁在什么情况下）、**可观察结果**（看到什么）、**判定方式**（怎么验）。

## 不合格的 AC 与改法

| 原写法 | 问题 | 改成 |
|---|---|---|
| 导出要快 | 没有阈值 | 「1 万行导出 P95 < 30 秒，压测脚本可复现」 |
| 体验流畅 | 不可判定 | 拆成具体交互：首屏 < 1 秒、列表滚动无卡顿（用录屏判定） |
| 用户满意 | 不是系统行为 | 「上线两周后 NPS ≥ 40，问卷口径见 §7」 |
| 支持多种格式 | 范围无边 | 「本期支持 CSV；XLSX 列入非目标」 |
| 系统要稳定 | 无法验收 | 「连续 24 小时压测错误率 < 0.1%」 |

## 判定方式只能这四种

1. 看界面状态（页面元素、提示文案）。
2. 看数据（数据库、埋点、报表）。
3. 跑命令（测试脚本、压测、迁移脚本）。
4. 看日志（错误码、审计记录）。

写不出判定方式的 AC，说明需求还没定义清楚，不是测试的问题。

## 自检

- [ ] 每条 AC 只验一件事
- [ ] 没有「并且 / 或者」连接两个结果
- [ ] 没有形容词型标准（流畅、良好、尽量、大概）
- [ ] 判定方式是可执行的，别人照着能复现
