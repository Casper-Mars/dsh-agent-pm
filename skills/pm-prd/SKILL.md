# 编写需求文档

一次处理一个需求，产出可评审的诊断卡片或 PRD。可评审的标准是：用户不需要看技术方案，就能决定做还是不做。

## 工作流程

1. **归一化输入。** 先判断手上是什么：一句话想法、半成品 PRD、纪要、截图，还是社区讨论。缺关键项时一次问全五问（话术与证据分级见 `references/diagnosis.md`），问不到就按最低风险假设继续，并把假设写进未决。只有连问题都无法定义时才停。
2. **判断值不值得做。** 用证据给信号定级，不靠热情。弱信号或伪信号：交诊断卡片——等级、理由、证伪条件、下一步，然后停止，不写 PRD。没有证据：按 `references/mining.md` 采集，平台细则见 `references/v2ex.md`、`references/hackernews.md`、`references/producthunt.md`，采完回到第 1 步。
3. **定范围。** 写目标、至少三条非目标、角色与触发场景、主流程与异常路径、本期 / 下期 / 明确延后。非目标决定边界；没有非目标，范围就无法评审。
4. **定验收与指标。** 每条 AC 三要素齐全，一条只验一件事（写法见 `references/ac-examples.md`）。每个指标有口径、基线、目标值、窗口、来源。AC 是设计和测试的输入；写不清，就是把问题丢给下游。
5. **自检并交付。** 按 10 项判据逐条验（见 `references/checklists.md`）。不过就改对应步骤，带着失败证据，不重写全文。语言纪律见 `references/language.md`，事实 / 结论 / 范围三查见 `references/doc-checks.md`。通过后按 `assets/prd-template.md` 生成内容，再按「输出」选择载体交付，停。

## 输出

诊断卡片或 PRD 落在哪里，由当前场景决定，不要默认写本地文件：

1. **用户指定了载体**：要飞书文档就创建飞书文档并回链接；要本地文件就给路径；要贴到 Issue / PR 就贴到对应位置。
2. **用户没指定，但场景有明确载体**：在工作目录的 git 仓库里 → 写本地文件（默认 `docs/prd/<主题>.md`）并提交；在飞书会话里且产物需要共享或留存 → 建飞书文档并回链接；只是一次性判断 → 直接在对话里给诊断卡片。
3. **判断不了**：问一句「要本地文件、飞书文档，还是只在对话里给结论？」；用户想先看内容时，先在对话里给摘要，确认后再落到选定载体。

默认优先级：有仓库且需长期维护 → 本地文件；需多人评审或共享 → 飞书文档；一次性判断 → 对话。无论落在哪里，最后都回一个可访问的位置（路径或链接）和 commit（如果有）。

## 规则

- 点赞、收藏、注册数只能用来排序候选，不能当需求强度。
- 结论不能强于证据等级；E4 转述不能说成「强需求」。
- 不编造数据、条目、热度或用户原话。
- 弱信号不硬写 PRD；交诊断卡片并说明升级需要什么证据。
