# 编写需求文档

一次处理一个需求，产出可评审的需求文档。可评审的标准是：用户不看技术方案，就能决定做还是不做。

## 三种厚度

流程不变，文档厚度由需求卡首行的 `级别：<weight>` 决定；没写按 `m` 处理。

| weight | 产物 | 上限 |
|---|---|---|
| `xs` | 一句话需求，模板 `assets/one-liner.md` | 5 行 |
| `s` | 变更卡，模板 `assets/change-card.md` | 1 屏 / 600 字 |
| `m` / `l` | 九章 PRD / PR-FAQ | 既有规范 |

定级依据：用户可观察行为变不变、对外契约变不变、有无需要人拍板的取舍。三问全是否 → `xs`；只改行为、无新契约 → `s`；改契约或有取舍 → `m` 以上。

## Iron Law

> 没有一条能挡住范围蔓延的非目标，不算 PRD。（仅适用 `m` / `l`；`xs` / `s` 的另一条铁律是：没有可观察的验收，不算需求。）

## 什么时候用 / 不用

- 用：新需求定义、旧 PRD 修订、PRD 评审、AC 补齐、给管理层的 PR-FAQ。
- 不用：判断值不值得做（先走 `pm-discovery`）、排优先级（`pm-prioritize`）、技术方案。

## 流程

0. **按级别分流**：`xs` 用 `assets/one-liner.md`、`s` 用 `assets/change-card.md`，写完直接跳到第 8 步；`m` / `l` 走完整 1–7 步。
1. **确认输入**：读需求卡首行的 `级别：<weight>`（没写按 `m`）；判断手上是诊断卡片、一句话想法、纪要还是旧 PRD。没有诊断结论时，先回 `pm-discovery`，不跳过证据。
2. **写目标与非目标**：每个目标有指标、基线、目标值；每条非目标要能指出它挡住哪一次具体的范围蔓延（「不做什么 / 为谁不做 / 什么时候不做」按适用写），指不出的删掉。
3. **写用户与场景**：角色具体到职责，写出触发场景与现有替代方案。
4. **写范围**：本期 / 下期 / 明确延后三列；主流程逐步，异常覆盖空数据、超时、无权限、重复提交。
5. **写 AC**：每条三要素（前置、动作、可观察结果），一条只验一件事。写法见 `references/ac-examples.md`。
6. **写指标**：口径、基线、目标值、观察窗口、数据来源，五项缺一不可。
7. **写依赖、风险、未决**：无未决直接写「无」；有未决则每项有决策人、截止时间、未定前默认动作。
8. **自检**：`m` / `l` 按 `references/checklists.md` 十项逐条验；`xs` / `s` 只查两条：AC 可观察、字数不超上限。语言纪律见 `references/language.md`，事实/结论/范围三查见 `references/doc-checks.md`。
9. **按模板成文**：`xs` / `s` 已在第 0 步用模板产出，不重复；`m` 用 `assets/prd-template.md`，面向管理层或从用户视角倒推时用 `assets/prfq-template.md`。
10. **检查可交接性**：DoR 见 `references/dor.md`，不过就不算完成。

## 门禁

`m` / `l` 适用全部九道；`xs` / `s` 只过第 5 道（AC 三要素）与第 7 道（未决），另加字数上限。

| # | 门禁 | 通过线 | 不过怎么办 |
|---|---|---|---|
| 1 | 目标 | 每个目标有指标、基线、目标值 | 补不齐就标条件版，不进评审 |
| 2 | 非目标 | 每条能指出挡住的越界行为；条数由范围决定，不凑数 | 退回第 2 步，删或补 |
| 3 | 场景 | 角色 + 触发 + 现有替代 | 退回第 3 步 |
| 4 | 范围 | 本期/下期/延后都有内容 | 退回第 4 步 |
| 5 | AC | 三要素齐全、一条一事、可复现 | 退回第 5 步 |
| 6 | 指标 | 五要素齐全 | 退回第 6 步 |
| 7 | 未决 | 无未决写「无」；有则每项有主与截止 | 补决策人或截止 |
| 8 | 语言 | 禁用词 0 命中、三查通过 | 按 `references/language.md` 改 |
| 9 | DoR | `references/dor.md` 全绿 | 不交接 |

## 输出契约

需求产物按 weight 选，不默认九章：

- `xs` → `assets/one-liner.md`：问题 / 期望 / 验收 / 级别，≤5 行。不写非目标、指标、分期。
- `s` → `assets/change-card.md`：问题 / 期望行为 / 范围（做与不做）/ 验收 2–5 条 / 风险与依赖，≤1 屏（600 字）。
- `m` / `l` → 九章：问题与证据、目标与非目标、用户与场景、方案与主流程、范围与分期、验收条件、指标、依赖与风险、未决项。九章都要出现，缺章不算完成；「未决项」无内容时只写一句「无未决」，不编条目。

共同底线：验收条件必须有且可观察；文档规模不得超过决策规模；`m` / `l` 交付必须附一页决策简报（见 `pm-brief`）。

交付位置：用户指定载体优先；有仓库写 `docs/prd/<主题>.md`；需共享建飞书文档；一次性判断在对话里给结论。最后必须回一个可访问位置（路径或链接）。

## 反合理化

| 借口 | 现实 |
|---|---|
| 非目标先不写了 | 没有非目标就无法评审范围，必然返工 |
| AC 开发会补 | AC 是设计与测试的输入，不是实现产物 |
| 指标上线再看 | 没有基线就没有结论，只有故事 |
| 这个很简单不用写 | 简单要有判据：行为唯一、无取舍、无新契约才是一句话需求；判不准就升一级，不是不写 |
| 反正不确定，按九章写保险 | 文档规模不得超过决策规模；判不了先写明依据再定级，不靠堆章节免责 |
| 老板催，先出个初稿 | 初稿可以，但必须标「条件版」与缺失项 |
| 多写几条显得完备 | 读者要判断，不要字数。删掉后没有任何决策会变的条目，就是凑数 |
| 没有未决也留一行，省得说不全 | 零未决是正常状态，写「无」即可；空槽会被读成待填 |

## 红旗

- 在需求文档里写实现方式或技术选型。
- 为三行修复写九章 PRD；`xs` 需求里出现指标、分期或数据模型章节。
- AC 写成「体验流畅」「速度快」。
- 非目标写成「暂不做」但没有原因。
- 指标只有目标值，没有口径与来源。
- 用「已确认」代替证据链接。
- 为了让评审通过，放宽 AC。
- 为过门禁而填条目：凑条数、凑章节、留空槽。

## 反例（真实产出，勿模仿）

- 把「若已在其他分支补上，请以最新代码为准」写成「未决项」：读者本来就会这么做，没有缺失输入，也没有待办的人。
- 为凑条数写「不给 description 加任何内容规范或校验」：需求方原话是「描述就是一个字符串，哪有那么复杂」。

判据：删掉这一条，是否有决策会变、是否有风险失控？「否」就是凑数。

## 交接

- 交接物：PRD 链接、证据清单、未决项（无则写「无」，有则每项有主与截止）。
- 移交对象：CTO 做技术判断与拆解；`pm-handoff` 做开发交接与变更控制。
- 交接后 AC 变更走变更单，不事后追认。
